# Shared agent instructions

1. On every run, read the current issue, status, assignee, trigger, approved scope and revision, latest handoff, and any linked candidate, tests, or deployment records. On a parent, read the current child list and stages. Reconcile those facts before acting.
2. Follow the authority of your role. The current step owner advances the issue. An invited reviewer posts findings. If the current step or assignee changed, stop writes and leave a concise note where useful.
3. Before handing off, record the outcome, exact revision or durable artifact, verification evidence, unresolved items, and next action. Keep everything the next run needs in Git or a durable, accessible project location. Reference the existing path and revision on the issue when the recipient can reach it. Attach only when access, preservation, or an explicit request calls for it. A model session or local worktree may speed up work but carries no required state.
4. Before repeating an external action, check whether it already happened. Resume matching child issues, pull requests, and release records. Never claim that a run, test, deployment, or approval succeeded without evidence for the relevant revision.
5. Obey human approval and cancellation. A changed spec or release candidate invalidates the corresponding earlier approval. Material scope changes return to Shape.
6. Use the documented tools and permissions for your role. Escalate a missing tool, permission, or decision with the last durable checkpoint and a concrete next action.
7. Use the issue-label vocabulary in [the delivery workflow](../workflows/README.md#labels). Use `discovery` for research and prototypes. If an approved label is unavailable, leave the issue unlabelled.
8. Use the project's managed checkout and keep disposable files scoped to the run. For code handoffs before release approval, record the exact local commit SHA and share accessible issue evidence. Follow the publication rule in the delivery runbook. Omit automated co-author trailers, provider bylines, and session links. Start dependent work from its recorded, verified input revision.
9. Collaborate with the humans identified in the current project or issue. When their direction conflicts, summarize the choices and ask the designated decision-maker for that scope. Verify the authorized actor and exact candidate at approval gates.
10. Keep project files within the existing project tree. Use the managed checkout for code and the project's visible, Git-ignored `artifacts/<issue-id>/` folder for durable local working files. Use run-scoped temporary storage for disposable evidence and remove your temporary files when done. Use an existing approved tool-managed checkout when needed. Ask before creating a new sibling project or scratch directory in the workspace. Preserve existing files you did not create.
